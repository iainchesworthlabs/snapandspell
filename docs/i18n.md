# Languages

The application is offered in eight languages: English (`en`, the source), French (`fr`), Spanish
(`es`), German (`de`), Yiddish (`yi`), Hebrew (`he`), Chinese (`zh_CN`) and Japanese (`ja`). The
Language row in the parent area offers those eight and System, which is the device's language when it
is one of them and English otherwise.

## What is translated

The chrome: every label, sentence, accessible name and message. Not the board: the dice letters, the
words in the tray, the word list and the phonics content are English, because the game is an English
word game.

## Origin and review

| Language | Catalogue | Origin | Review |
| --- | --- | --- | --- |
| English | `apps/app/translations/sns_en.ts` | written by the author | the author |
| French, Spanish, German, Japanese | `sns_fr.ts`, `sns_es.ts`, `sns_de.ts`, `sns_ja.ts` | mechanical translation | none yet |
| Chinese (Simplified), Hebrew, Yiddish | `sns_zh_CN.ts`, `sns_he.ts`, `sns_yi.ts` | mechanical translation | none yet; drafts |

A translation is not a reviewed translation until this table says so. The wording a child and a
parent see is part of the literacy review, with the phonics content. Hebrew and Yiddish read right to
left: the chrome mirrors and the board never does ([Application design](design/application.md#languages-right-to-left-and-fonts)).

## How it works

Every user-facing string is `qsTr()`. The sentences of an area live in that area's wording file
(`ParentWording.qml`, `ScanWording.qml`, `SoloWording.qml`, `HomeWording.qml`). `lupdate` writes the
catalogues from the QML sources and `lrelease` compiles them into the application at build time.
`LanguageManager` installs the catalogue and the layout direction before the window is built, and a
change in the parent area retranslates the screens at once. The setting is stored as `zh_CN`;
an older store that says `zh` is migrated when it is read.

## Changing a string

1. Change the `qsTr()` text in the wording file.
2. Regenerate the catalogues: `cmake --build <build> --target sns_update_translations`.
3. Translate the new messages in each `.ts` file, or leave them `unfinished` for the draft languages
   and say so in the pull request. `i18n.catalogues` fails when a catalogue differs from what `lupdate`
   writes, and `language_test` fails when a catalogue lacks a message or has an unfinished one.
4. If the translation uses a character the bundled Chinese, Japanese or Hebrew face lacks, remake the
   faces: `python3 tools/design/make_noto_subsets.py --upstream <dir with the three upstream Noto
   files> --out assets/fonts` (needs fontTools; the upstream files and their addresses are in the
   script's header) and commit the six `.ttf` files. `language_test`'s "the bundled faces carry every
   character of every catalogue" names the characters that are missing. The web has no system fonts,
   so there is no fallback to rely on.

## Checks

`apps/app/tests/unit/language_test.cpp` (every language has a catalogue with the same messages,
directions, the bundled faces carry every character of every catalogue), `apps/app/ui-tests/tst_rtl.qml` (the
chrome mirrors, the board does not) and `i18n.catalogues` (the catalogues are what `lupdate`
regenerates). Not yet checked: text overflow in the longest translations, and number and date
formatting by locale.
